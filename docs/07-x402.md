# Paying for APIs per request: Leash and x402

x402 is the HTTP convention for paid requests: a server answers `402 Payment Required` with a
`PAYMENT-REQUIRED` header naming what it accepts, the client pays and repeats the request with a
`PAYMENT-SIGNATURE` header, and the server settles the payment through a facilitator and answers with
a `PAYMENT-RESPONSE` header. Version 2 of the protocol is what everything here speaks
([spec](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md)).

NEAR is one of x402's networks: `near:mainnet` and `near:testnet`, scheme `exact`, any NEP-141
token. Its standard payload is a signed delegate action for one `ft_transfer`, which only a
full-access key can produce, because a function-call key cannot attach the one yoctoNEAR a token
transfer needs. A Leash agent holds a function-call key on purpose, and its money sits in the
owner's vault, not on the agent. So Leash is its own transfer method on the same network binding.

## The Leash method

A resource server that takes Leash payments lists this among its `accepts`:

```json
{
  "scheme": "exact",
  "network": "near:testnet",
  "amount": "10000",
  "asset": "3e2210e1184b45b64c8a434c0a7e7b23cc04ea7eb7a6c3c32520d03d4afcb8af",
  "payTo": "vendor.testnet",
  "maxTimeoutSeconds": 120,
  "extra": { "assetTransferMethod": "leash", "contract": "leash.frankolien.testnet", "paymentFlow": "upfront" }
}
```

`amount` is in the token's units (USDC has six decimals, so `10000` is one cent). `asset` is the
token contract. `extra.contract` names the Leash contract whose agents can pay here.

The agent's payload is its signed pay intent, the same instruction it would hand the Leash relay:

```json
{
  "x402Version": 2,
  "resource": { "url": "https://leash.frankolien.com/api/paid/sample" },
  "accepted": { "...the requirements it chose, echoed back..." },
  "payload": {
    "intent": "{\"contract\":\"leash.frankolien.testnet\",\"owner\":\"frankolien.testnet\",\"key\":\"ed25519:...\",\"action\":\"pay\",\"to\":\"vendor.testnet\",\"amount\":\"10000\",\"memo\":\"x402 https://leash.frankolien.com/api/paid/sample\",\"payment_id\":\"...\",\"expires_at\":1793302210784795400}",
    "signature": "base64 ed25519 signature over leash-intent:<intent>"
  }
}
```

The intent names the recipient and amount, so a facilitator or a server that forwards it cannot
redirect or resize the payment; the signature is over the exact text; `payment_id` means the contract
never pays it twice; `expires_at` is in nanoseconds and at most an hour out.

## The facilitator

The Leash site is a facilitator for this method, at `https://leash.frankolien.com/api/x402`:

| Route | Does |
| --- | --- |
| `GET /supported` | `{ kinds: [{ x402Version: 2, scheme: "exact", network: "near:testnet", extra: { assetTransferMethod: "leash", contract } }], extensions: [], signers }` |
| `POST /verify` | Checks the payload against the requirements and the signature against the key, then asks the contract's `check` view whether the owner's limits would allow it. Writes nothing. |
| `POST /settle` | The same checks, then delivers the intent to the contract through the relay (`pay_signed`), which applies the limits and moves the USDC. Answers `{ success, transaction, network, payer, amount }`. |

Both take the spec's body, `{ x402Version, paymentPayload, paymentRequirements }`, and answer with the
spec's codes: `invalid_payload` when the intent is malformed, signed by another key, expired, or pays
someone or something other than the requirements; `invalid_payment_requirements` when the payload
accepted other terms or the key pays in another token; `invalid_network`, `unsupported_scheme`,
`invalid_x402_version`; and `insufficient_funds` when the owner's limits refuse it, with the contract's
reason in `invalidMessage` or `errorMessage` ("over per-payment cap", "recipient not in allowlist").

No API key is needed. Delivering someone's signed intent pays only whom they signed for, under their
owner's limits, and the relay brakes how much gas one owner can burn.

## For a resource server

In this repo, `paywall` in `web/lib/server/x402.ts` is the whole thing: call it first; it answers the
402 when there is no payment, settles when there is one, and hands the route the `PAYMENT-RESPONSE`
header to attach. `web/app/api/paid/sample/route.ts` is a one-cent example, live at
`https://leash.frankolien.com/api/paid/sample`.

Leash uses the protocol's `upfront` flow, settling before the route runs, because the contract settles
atomically: the server is never left having served a request whose payment then failed. A server
using the default `authorization` flow (verify, serve, settle) works too.

Another server can use the same facilitator by pointing its settle calls at
`https://leash.frankolien.com/api/x402/settle` (`X402_FACILITATOR_URL` in this repo's helper), or with
the official SDK's `HTTPFacilitatorClient` and a scheme that produces the payload above.

## For an agent

`leash_fetch` in the MCP server does the client side: it fetches the URL, reads the 402, picks a
Leash way of paying on the agent's network and token (the cheapest if several), refuses prices over
`max_usdc` (1.00 by default) or over the owner's limits before anything is sent, signs the intent,
repeats the request with `PAYMENT-SIGNATURE`, and returns the content with the on-chain transaction.
The owner's log shows the payment with the URL as its memo, as any other payment. A task's child key
can pay too, with `task`.

When a server only takes the standard NEAR payload, or other networks, the tool says so in words
and pays nothing.

## What this is not

Leash does not settle the standard `near:*` `exact` payload (the signed delegate action), since no
Leash key can produce one; fastnear's facilitator does. Nothing here changes the contract: `pay_signed`
is the same method the relay has always delivered.
